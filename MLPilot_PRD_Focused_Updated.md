# MLPilot — Product Requirements Document (Focused Product Edition)

**Working name:** MLPilot  
**Category:** Agentic ML experimentation and decision-support platform  
**Status:** Product and implementation specification  
**North star:** Help people run better ML experiments, understand what the evidence says, and reproduce the resulting model.

---

## 1. Executive Summary

MLPilot is an open-core, AI-assisted ML experimentation workspace for students, independent developers, researchers, freelancers, and small teams.

It is not primarily a data-cleaning product, generic AutoML wrapper, notebook replacement, or enterprise MLOps suite.

Its core loop is:

**Hypothesis → Controlled experiment → Evidence → Decision → Next hypothesis**

A user supplies a tabular dataset, a prediction objective, and constraints. MLPilot establishes a reproducible baseline, proposes specific experiments, executes approved experiments through deterministic ML code, records the results and rationale, and recommends the next useful experiment.

The LLM proposes and interprets. Deterministic code validates experiment specifications, performs data transformations, creates splits, trains models, calculates metrics, enforces budgets, and stores artifacts. The LLM must never invent metrics or independently execute arbitrary generated Python.

### Product promise

> MLPilot helps you understand not just which model scored highest, but what you tried, what the evidence showed, what you learned, and what is worth trying next.

The initial product should be useful locally and without a paid LLM API. A public/open-source edition is a first-class outcome, not a fallback. A hosted service or ML delivery service can be developed if users demonstrate demand.

---

## 2. Product Goals and Non-Goals

### Goals

1. Build a technically credible ML project that demonstrates practical ML fundamentals and sound engineering.
2. Help users run structured, reproducible experiments rather than random model trials.
3. Make experiment history, hypotheses, evidence, and decisions inspectable.
4. Provide a compelling end-to-end workflow on ordinary tabular datasets.
5. Remain useful with no LLM configured; AI should improve the workflow, not be a dependency for basic ML.
6. Support an open-source local workflow and allow later commercial hosted services.
7. Integrate with external data-preparation tools, including DataClean, without requiring them.

### Non-goals for the first release

- Reimplementing a full data-cleaning product.
- Competing feature-for-feature with mature AutoML libraries.
- Supporting every ML modality.
- Production model hosting, monitoring, retraining, billing, enterprise SSO, or multi-tenancy.
- Arbitrary code execution generated by an LLM.
- Claiming that an LLM has discovered a causal relationship from predictive experiments.

## 3. Users and Initial Use Cases

### Primary users

- Students and ML learners who want a serious, explainable project workflow.
- Python-capable developers who can train a model but lack a systematic experiment process.
- Independent researchers and Kaggle participants who need reproducible experiment tracking.
- Freelancers and small teams producing ML prototypes or client deliverables.

### Initial use cases

- Churn or retention classification.
- Lead scoring and conversion prediction.
- Tabular fraud/risk classification (with appropriate caveats).
- Regression for demand, prices, or operational metrics.
- Comparing feature hypotheses, validation choices, model families, and thresholds.

The first release targets CSV-based tabular binary classification, multiclass classification, and regression. Other tasks are future extensions.

## 4. Positioning and Differentiation

### Positioning

**Agentic ML experimentation and decision support.**

Do not lead with “AI builds the best model automatically” or “all-in-one AutoML.” The product should be differentiated by the quality and transparency of its experiment loop, not by claiming every underlying ML component is novel.

- **Primary goal:** Solve something inside the ML workflow that other tools genuinely don't solve, or that users didn't realize could be solved — the target reaction is *"this fixes something nobody else fixed,"* not *"this is a cheaper DataRobot."*
- **Backup floor, not the main target:** If the primary goal doesn't fully land, fall back to being an equally-or-more-efficient alternative to costly incumbents, at better pricing and speed, easy to integrate.

### Differentiator A — Hypothesis-led experiments

Every agent-proposed experiment must state:

- Hypothesis and rationale.
- Exact change being tested.
- Required columns and assumptions.
- Validation strategy and primary metric.
- Expected benefit, uncertainty, and risk.
- Estimated compute/API cost.
- What result would support or reject the hypothesis.

Where feasible, compare one controlled change against a parent experiment. Multi-change experiments must identify their changes and avoid claiming which change caused the outcome.

### Differentiator B — Experiment memory and decision provenance

Each experiment records:

- Parent experiment and branch.
- Dataset fingerprint/version.
- Objective and metric definitions.
- Feature set and preprocessing configuration.
- Model and hyperparameters.
- Validation and split configuration.
- Metrics by fold and aggregate.
- Runtime, resource usage, and LLM cost where measurable.
- Hypothesis, result interpretation, decision, and rationale.
- Code/configuration version and artifact references.

Users can inspect why a model or feature was retained and see rejected or inconclusive branches.

### Differentiator C — Next-experiment recommendation

The agent should use the project objective, previous experiments, uncertainty, constraints, and budget to recommend a next experiment. It should explain which uncertainty the experiment is intended to resolve and why it is not redundant.

Initially, recommendation quality can be rule-guided and LLM-assisted. Do not claim mathematically calibrated expected information gain until it is actually implemented and evaluated.

### Differentiator D — Trustworthy execution

- Metrics are calculated by deterministic code.
- Validation and preprocessing are performed without leakage.
- The test set is sealed from iterative experiment selection where a holdout is used.
- LLMs cannot silently change data or run arbitrary host commands.
- Every AI explanation references stored evidence.
- Users can inspect, approve, modify, or reject proposals.

## 5. Relationship to DataClean and Other Tools

MLPilot must not be designed as a competing clone of the friend's DataClean project.

### Product boundary

**DataClean's intended center:** data quality, cleaning decisions, leakage-aware preparation, and producing a defensible ML-ready dataset/model workflow.

**MLPilot's center:** experiment hypotheses, controlled runs, experiment lineage, evidence interpretation, and choosing what to investigate next.

Some overlap is appropriate and necessary: MLPilot needs dataset ingestion, basic profiling, validation, baseline training, and leakage safeguards. These should be built only to the extent required to make the experimentation product independently usable.

### Adapter architecture

Define a stable `DataPreparationProvider` interface. Initially implement a small native provider sufficient for the MLPilot workflow. Later, optionally add a DataClean adapter if both parties agree on API, ownership, licensing, data handling, and maintenance.

The system must remain functional if DataClean is unavailable.

Possible interface:

```python
class DataPreparationProvider:
    def profile(self, dataset, context): ...
    def assess_readiness(self, dataset, context): ...
    def detect_leakage(self, dataset, target, context): ...
    def prepare(self, dataset, config, context): ...
    def export_pipeline(self, preparation_id): ...
```

The interface is a boundary, not a reason to implement a large plugin ecosystem in the MVP. Keep the first version simple.

### Integration rules

- No copying DataClean's implementation without permission and an agreed license.
- No dependency on DataClean for core experiment execution.
- No assumption that the integration will happen.
- Compare correctness, leakage handling, reproducibility, API stability, runtime, and maintenance before selecting a provider.
- Keep the integration optional and clearly attribute any external component.

## 7. MVP Scope

The MVP is a polished, local-first or single-user web application that proves the central loop. It is not the full SaaS.

### Required

1. Create a project with name, objective, target, task type, primary metric, and budget.
2. Upload CSV and inspect schema, dimensions, missingness, class balance, cardinality, and basic distributions.
3. Show readiness and validation/leakage warnings with evidence and limitations.
4. Select a supported validation strategy and establish a deterministic baseline.
5. Generate structured experiment hypotheses using an LLM, with a manual fallback.
6. Support a limited set of safe, predefined experiment actions.
7. Run experiments deterministically through scikit-learn pipelines and approved model implementations.
8. Record experiment configs, metrics, status, runtime, and artifacts.
9. Compare a candidate with its parent and current champion.
10. Show an experiment history/graph with accepted, rejected, failed, and inconclusive runs.
11. Provide an evidence-grounded explanation and a next-experiment recommendation.
12. Enforce experiment, runtime, and optional API budgets.
13. Export a reproducible training script, model artifact, metrics, experiment history, and model card.
14. Include a demo dataset and a scripted demonstration.

### Explicitly out of MVP

- Team workspaces and collaboration.
- Billing, subscriptions, and SaaS usage metering.
- Hosted inference and one-click cloud deployment.
- Drift monitoring and automatic retraining.
- Enterprise controls, SSO, SCIM, VPC, or on-prem enterprise packaging.
- Complex data connectors and data warehouses.
- Time series, NLP, image, multimodal, and other advanced task families.
- A large model zoo or unrestricted hyperparameter search.
- Learned experiment-utility models or claims of statistically calibrated information gain.

## 8. Functional Requirements

### 8.1 Project and objective

A project stores:

- Project name and description.
- Dataset and fingerprint.
- Target and task.
- Primary metric and secondary metrics.
- Validation strategy and random seeds.
- User-defined constraints and budget.
- Experiments, artifacts, decisions, and selected model.

The user must explicitly confirm the target, metric, and validation approach before an experiment campaign begins.

### 8.2 Dataset ingestion and profiling

Initial input: CSV. Parquet can follow after the core flow works.

Deterministic profiling includes:

- Rows, columns, types, missing values, duplicates.
- Unique counts, constant and ID-like columns.
- Numeric distributions and categorical cardinality.
- Target distribution and class imbalance.
- Basic date detection and suspicious columns.
- Dataset fingerprint and immutable original upload.

Do not send full datasets to an LLM by default. Provide structured metadata, carefully sampled values, and user-controlled privacy settings.

### 8.3 Data readiness and leakage safeguards

Start with transparent, testable checks rather than a single opaque readiness score.

Checks may include:

- Target included among predictors or duplicated/derived target fields.
- Features that appear to be post-outcome or unavailable at prediction time.
- Duplicate rows and duplicate entities across splits.
- Preprocessing fit outside training folds.
- Temporal leakage when time-based prediction is intended.
- Group/entity leakage where relevant.
- Suspiciously high performance requiring investigation.

Every warning must state what was detected, why it matters, confidence/limitations, and a suggested review action. Do not silently remove columns. A warning is not proof of leakage.

### 8.4 Validation and baseline

Support initially:

- Stratified K-fold for suitable classification data.
- K-fold for suitable regression data.
- Holdout where justified.
- A basic chronological split only when the user identifies a temporal prediction problem and the implementation supports it safely.

Keep preprocessing inside the cross-validation pipeline. Make random seeds, fold definitions, and metric calculations reproducible.

Initial models should be deliberately limited: Dummy, Logistic/Linear models, Random Forest, and one gradient-boosting option where installation and runtime allow. Add CatBoost/XGBoost/LightGBM as optional integrations, not mandatory dependencies.

### 8.5 Experiment specification and safe action space

An experiment is a validated structured configuration, not arbitrary generated code.

Initial action families:

- Compare a supported model family against the baseline.
- Add or remove an approved feature transformation.
- Test a small, bounded hyperparameter configuration.
- Compare a justified metric/threshold strategy without using the sealed test set.
- Test a preprocessing alternative when it can be fitted within each training fold.

Every proposal includes its hypothesis, exact changes, required columns, risk, budget estimate, and evaluation plan.

Reject unsupported transformations, missing columns, unsafe configuration, excessive budgets, and invalid combinations before execution.

### 8.6 Experiment runner

The runner must:

- Execute only allowlisted actions and model classes.
- Use deterministic pipelines and controlled configuration.
- Fit all learned preprocessing within training folds.
- Keep validation and test data roles explicit.
- Enforce row, memory, runtime, and experiment limits where practical.
- Record failures with actionable error messages.
- Never execute LLM-generated Python on the host.

For a local-first MVP, begin with a separate worker process and strict resource limits. Container isolation is required before offering execution of untrusted user workloads in a hosted multi-user service.

### 8.7 Experiment record

Minimum fields:

```json
{
  "experiment_id": "stable-id",
  "parent_id": "parent-or-null",
  "dataset_fingerprint": "hash",
  "hypothesis": "structured hypothesis",
  "change_spec": {},
  "model_config": {},
  "preprocessing_config": {},
  "validation_config": {},
  "metrics": {},
  "fold_metrics": [],
  "runtime_seconds": 0,
  "status": "queued|running|completed|failed|cancelled",
  "decision": "keep|reject|inconclusive|pending",
  "decision_reason": "",
  "artifact_refs": [],
  "agent_provider": "",
  "agent_model": "",
  "created_at": ""
}
```

Never hardcode illustrative metrics as actual results.

### 8.8 Evidence evaluator and agent

Python computes metrics, fold variation, and comparisons. Where appropriate and correctly implemented, report uncertainty or paired comparisons; do not overstate statistical significance.

The LLM may summarize:

- What changed.
- What the observed results show.
- Which constraints were met or violated.
- What remains uncertain.
- Which next experiment could distinguish plausible explanations.

Each numerical statement in the explanation must be traceable to stored results. The interface should distinguish measured facts from agent interpretation.

### 8.9 Experiment graph

Display parent/child relationships, status, key metric delta, and decision. A table/list view must remain available for accessibility and large histories.

The graph should answer:

- What was tested?
- What changed?
- Compared with which run?
- What happened?
- Why was it kept, rejected, or left inconclusive?
- What should be tested next?

### 8.10 Export

Initial exports:

- Model artifact where supported.
- Reproducible training script.
- Prediction example/script.
- Requirements or environment file.
- Metrics and experiment history in machine-readable form.
- Model card with purpose, data assumptions, validation, metrics, limitations, and intended use.

Exported code must not contain API keys or secrets.

## 9. Agent Design and Autonomy

### MVP: Suggest and approve

The agent proposes an experiment. The user inspects and approves, edits, or rejects it. Execution begins only after deterministic validation.

### Later: Bounded assisted mode

Safe experiments may run automatically within user-defined limits. The user can pause or cancel the campaign.

### Later: Autonomous campaign

Only after the experiment engine and evaluation suite are reliable. The agent may choose among approved actions and budgets; it may not alter hard constraints, access arbitrary files, execute arbitrary code, or deploy a model without explicit approval.

### Recommendation quality

Evaluate the agent on more than final model score:

- Valid proposal rate.
- Duplicate/redundant experiment rate.
- Useful experiment rate as judged against a documented rubric.
- Invalid/leakage-causing proposal rate.
- Improvement and stability per unit of compute.
- Experiments needed to reach a predefined objective.
- Whether explanations match stored evidence.

Do not claim the agent is better than a human data scientist without a credible benchmark.

## 10. Architecture

Keep the first implementation modular but avoid premature microservices.

```text
React / TypeScript UI
        |
FastAPI application
        |
Project + Experiment Orchestrator
   |           |             |
ML Engine   AI Provider   Persistence
   |           |             |
Safe Runner  Provider      SQLite initially
   |         adapters      PostgreSQL later
   |
Metrics + Artifacts
   |
Experiment history / graph / exports
```

### Recommended initial stack

- Frontend: React, TypeScript, Vite, Tailwind.
- Backend: Python, FastAPI, Pydantic.
- ML: pandas, NumPy, scikit-learn; optional boosting libraries.
- Persistence: SQLite for local MVP; keep repository interfaces suitable for PostgreSQL later.
- Artifacts: local project directory with controlled paths; object storage later.
- Background execution: start with a bounded local worker/process. Introduce Redis and a distributed queue only when actual concurrency requires them.
- AI: provider interface with one reliable integration first; add additional providers only after the core workflow works.
- Tests: pytest for ML/validation/experiment logic; frontend tests for key user flows.

### Core interfaces

```python
class AIProvider:
    def generate_structured(self, task, context, schema): ...

class ExperimentRunner:
    def validate(self, spec, project_context): ...
    def run(self, spec, project_context): ...

class DataPreparationProvider:
    def profile(self, dataset, context): ...
    def assess_readiness(self, dataset, context): ...
    def prepare(self, dataset, config, context): ...

class ArtifactStore:
    def save(self, project_id, artifact, metadata): ...
    def get(self, artifact_id): ...
```

Do not implement every future interface as a complex plugin system in the first sprint. Establish only the seams needed for current modules and the optional DataClean adapter.

## 11. Security, Privacy, and Reliability

### Local-first default

- Keep datasets and artifacts local unless the user explicitly chooses hosted processing.
- Explain which metadata or samples are sent to an LLM.
- Support user-provided API keys without logging or exporting them.
- Do not store secrets in experiment records or client-visible logs.
- Validate file type, size, encoding, and parser errors.
- Use safe filenames and prevent path traversal.
- Provide deletion of local projects and artifacts.
- Never execute generated Python or shell commands directly on the host.

### Before hosted multi-user execution

Require isolated worker containers or equivalent sandboxing, resource quotas, tenant separation, authentication/authorization, encrypted secrets, rate limits, audit logging, retention controls, and security review. Do not market the local MVP as enterprise-secure or production-hardened.

### Reliability

- Every run has a status and recoverable failure record.
- Persist experiment configuration before execution.
- Handle cancellation and interrupted runs.
- Make random seeds and package versions visible.
- Never report a failed or skipped check as passed.
- Clearly label approximate, unavailable, or unverified measurements.

## 12. Product Experience

### Main screens

1. **Projects:** recent projects, status, and create/import actions.
2. **Project overview:** objective, dataset summary, baseline/champion, budget, and next recommendation.
3. **Data:** schema, distributions, warnings, and validation assumptions.
4. **Experiments:** searchable table with status, hypothesis, parent, metrics, cost, and decision.
5. **Experiment detail:** exact configuration, evidence, fold results, interpretation, artifacts, and decision controls.
6. **Experiment graph:** visual lineage with table fallback.
7. **Agent panel:** evidence, proposed action, rationale, risk, budget estimate, and approve/edit/reject controls.
8. **Model and export:** selected model, limitations, model card, and downloadable artifacts.

The first-run experience must include a sample project so users can understand the value without preparing their own dataset.

### Usability standard

A new user should be able to run a sample baseline and inspect a meaningful experiment without reading the source code or receiving a live walkthrough.

## 13. Open-Source and Commercial Strategy

### Open-source-first core

The core local workflow should be useful on its own:

- Local dataset processing.
- Deterministic experiment runner.
- Experiment history and graph.
- Provider interface and optional BYOK.
- Exportable artifacts.
- Documented configuration and reproducible demo.

Choose a license deliberately after reviewing dependencies and any third-party integrations. Do not promise a license or copy a friend's code before receiving agreement.

### Potential paid offerings — validate before building

- Hosted compute for experiments.
- Managed storage and collaboration.
- Team approvals and shared experiment workspaces.
- Hosted AI usage with transparent limits.
- Private deployment or support.
- ML experimentation and model-development services for clients.

The product must not depend on subsidized free API quotas to be economically viable. BYOK and no-LLM functionality should remain available.

### Early validation

Before building billing or enterprise features:

1. Publish a working demo and clear README.
2. Ask target users to try a real dataset.
3. Observe whether they understand the experiment graph and recommendations.
4. Record which tasks they repeat and where they get stuck.
5. Interview potential users about local versus hosted execution and willingness to pay.
6. Prioritize only validated recurring needs.

### Trust-building tactics for adoption

- **Public reproducible benchmark suite:** Compare 10–15 well-known Kaggle/OpenML datasets against human baselines or tools like AutoGluon/H2O. Publish this as early as possible to provide a high-leverage proof artifact.
- **ROI metric inside completed runs:** Display something like, "This would take ~N hours manually; this run took M minutes." This direct ROI visibility turns trials into conversions.
- **Shareable, team-visible experiment graph:** Ensure experiments can be viewed by a team, turning a single-player tool into a team seat license.
- **On-prem/VPC-deployable Docker image:** Support "your data never leaves your environment", which is a hard gate for orgs handling customer data.
- **Infrastructure Integrations:** Plug into existing infrastructure (e.g., read-only SQL from data warehouses, MLflow/W&B export) rather than forcing full migration into MLPilot's UI.

## 14. Success Metrics

### MVP engineering metrics

- Reproducible baseline on supported sample datasets.
- Leakage/preprocessing test suite passes.
- Every completed experiment can be reconstructed from stored configuration.
- No metric in AI text is unsupported by stored result data.
- Budget and cancellation controls work.
- Exported training script reproduces the reported result within documented tolerances.

### Product metrics

- Time for a new user to complete first baseline.
- Percentage of users who run a second experiment.
- Percentage who can explain why an experiment was kept or rejected.
- Useful versus redundant recommendations.
- Repeat use on another dataset.
- User-reported trust and clarity.
- Open-source issues, contributions, and successful independent usage.

Do not optimize only for star count, model leaderboard score, or number of features.

## 15. Release Definitions

### Prototype

A local application that profiles a dataset, trains a baseline, and records one experiment.

### MVP / Portfolio release

CSV upload, objective configuration, deterministic baseline, leakage/readiness warnings, bounded hypothesis-led experiments, evidence comparison, experiment history/graph, next recommendation, and reproducible export.

### Public beta

Polished onboarding, project persistence, robust error handling, optional BYOK, more validation/model options, demo datasets, documentation, and feedback collection.

### Hosted product

Only after validating demand: authentication, isolated workers, job queue, hosted storage, quotas, collaboration, billing, deployment, and operational monitoring.

### Long-term possibilities

Advanced experiment selection, domain playbooks, time-series support, team collaboration, deployment feedback, drift investigation, and private deployment. These are options, not MVP commitments.

## 17. Product Decision Rule

For every proposed feature, ask:

1. Does it improve experiment quality, evidence, reproducibility, or user understanding?
2. Is it necessary for the current release, or can it wait?
3. Is it a differentiating capability, commodity infrastructure, or optional integration?
4. Can an existing library or tool provide it safely?
5. Does it duplicate DataClean's intended center without improving MLPilot's experiment workflow?

Build the differentiating experiment intelligence. Integrate commodity infrastructure. Keep data preparation modular. Defer everything that does not help a user complete the core loop.

**Final product definition:**

> MLPilot is a local-first, open-core agentic ML experimentation workspace that helps users plan, run, compare, and learn from reproducible ML experiments, while preserving the evidence and decisions behind the resulting model.
